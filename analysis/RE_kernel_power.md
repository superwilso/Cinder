# RE — the SoC power framework from the kernel image, and what actually blocks deep idle

**Date:** 2026-09-04 · **Kernel:** Linux 3.10.26 (MT8590), extracted from the stock 1.02 `.UPG`
**Status:** everything below is read from the kernel image or from read-only device nodes.
**No suspend test was run.** The last one cost a forced reboot; see
`analysis/RE_early_suspend.md`. This document exists to replace that guesswork with the tables the
kernel actually ships.

Companion artifacts, all machine-generated by `analysis/kernel/extract_kernel_tables.py`:

- `analysis/kernel/spm_wakesrc.txt` — the SPM wake-source mask, decoded
- `analysis/kernel/power_golden_settings.txt` — MTK's reference register state per scenario
- `analysis/kernel/cxd3778gf_regmap.txt` — the codec's 210 named registers
- `analysis/kernel/mt6323_regmap.txt` — the PMIC's 425 named registers (pulled from the device)

## 1. The wake-source mask, and a correction

`spm_sleep_wakesrc` is initialised data at `0xc0b50458`, so its default is readable straight out of
the image without touching the device:

```
spm_sleep_wakesrc = 0x01204564
  bit  2  TWAM        ARMED
  bit  5  GPT         ARMED
  bit  6  EINT        ARMED
  bit  8  CEC         ARMED
  bit 10  LOW_BAT     ARMED
  bit 14  USB_PDN     ARMED
  bit 21  SYSPWREQ    ARMED
  bit 24  CPU1_IRQ    ARMED
  bit  1  PCM_TIMER   -
  bit  4  KP          -
```

The bit names are the kernel's own: they are the argument run for `spm_output_wake_reason`'s
`"[SPM] wake up by %s"` printk, in R12 bit order (`CPU PCM_TIMER TWAM TS KP GPT EINT CONN_WDT CEC
IRRX LOW_BAT CONN PCM_WDT USB_CD USB_PDN DBGSYS UART0 AFE THERM CIRQ CM4 SYSPWREQ ETHERNET
CPU0_IRQ..CPU3_IRQ`).

**KP — the keypad block — is not an armed wake source.** `kpd_pdrv_suspend` @0xc039d0a4 goes
further and calls `kpd_wakeup_src_setting(0)`, which writes 0 to the halfword at `0xf0011024`,
switching the keypad's own wake enable off on the way down.

**But the power key on this device is not on the keypad matrix.** `/proc/interrupts` shows
`mtk-kpd` (irq 148) at **0 counts** for the whole boot. The power key is handled by
`kpd_pwrkey_pmic_handler` → `kpd_pmic_pwrkey_hal`, i.e. through the PMIC. And the PMIC does have a
live path to SPM:

- `PMIC_EINT_SETTING` @0xc0443d74 calls `mt_eint_registration(150, 4, mt6323_pmic_eint_irq, 0)`
  and `mt_eint_set_hw_debounce(150, 1)` — **the MT6323 interrupt is EINT 150**.
- `EINT` (bit 6) **is** armed in the mask above.
- `upmu_set_rg_int_en_pwrkey` @0xc0450cc8 writes MT6323 register `0x160` (`INT_CON0`) bit 5.
  Read on the device: **`INT_CON0 = 0x0420`**, so bit 5 is set — the power-key interrupt is enabled.

So every link of `power key → MT6323 pwrkey INT → EINT 150 → SPM (EINT armed)` is present and
enabled. **This contradicts the diagnosis recorded after the wedge**, which assumed the device had
no wake source at all. It had one on paper.

**And "on paper" is exactly what caused the wedge in the first place.** The previous failure came
from trusting a code path that had never been executed in the state that mattered. This section is
the same class of evidence — a register read and a disassembly — and must not be treated as
permission to retry. What it changes is the *hypothesis*: the likely failure is not "nothing could
wake it" but "it woke, or never suspended cleanly, and the resume path did not complete". That is
a different bug and needs a different test.

## 2. `slp_pwake_time` — a wake that depends on nothing external

`/sys/module/mt_sleep/parameters/slp_pwake_time` is root-writable and currently `-1`.

`spm_get_wake_period` @0xc002c7dc takes it as its first argument: if it is `>= 0` the value is used
directly as a period in seconds; if negative the kernel derives one from the next alarm, defaulting
to **600 s** and capping at `0x1fa40` (129,600 s). The period then reaches
`spm_set_wakeup_event` @0xc002c5b8, which writes it to `SPM+0x35c` (`PCM_TIMER_VAL`) and — when it
is non-zero — ORs `0x0b160020` into `SPM+0x314` (`PCM_CON1`, `0x0b16` being the write key), setting
`PCM_TIMER_EN`.

This matters because it is a wake that does not depend on a button, a cable, an EINT, or any
userspace component: the SPM PCM script counts down in hardware while the CPU is off. It is the
closest thing available to an escape that depends on strictly less than what it rescues.

Two caveats, both unresolved and both load-bearing:

- `spm_set_wakeup_event` also writes `~wakesrc` to `SPM+0x810`
  (`SPM_SLEEP_WAKEUP_EVENT_MASK`), and `PCM_TIMER` (bit 1) is **not** in the default mask. Whether
  the PCM timer wakes the SoC through the R12 event mask or drives the PCM script directly
  (bypassing it) is **not** established here. Until it is, the timer is a hypothesis, not a
  guarantee.
- Waking the SoC is not the same as restoring a usable device. The wedge symptom was a dark screen
  and no USB, which is equally consistent with a resume that ran and left no working display.

## 3. Sony's own suspend instrumentation — `/sys/devices/platform/icx_pm_helper/`

This is the most useful thing found today, and it is Sony's, not MTK's. It records the last
suspend/resume cycle in detail, read-only:

| node | meaning |
|---|---|
| `spm_r12` | **the wake-source bitmask of the last suspend** — decode with the table in §1 |
| `spm_raw_sta`, `spm_isr`, `spm_event_reg`, `spm_debug_reg`, `spm_r13` | raw SPM state at wake |
| `spm_timer_out` | whether the PCM timer expired |
| `spm_cpu_wake` | which CPU took the wake |
| `eint_sta` | six words of EINT status — which external interrupt fired |
| `resume_count` | completed resumes this boot |
| `suspend_ts` / `resume_ts` / `suspend_kt` / `resume_kt` / `post_suspend_*` | timing either side |
| `boot_powerkey`, `boot_reboot`, `boot_wdt`, `boot_thermal`, `boot_deadbat`, `boot_reset` | boot cause |
| `resume_lock_ms` (rw) | Sony holds a **20,000 ms** wakelock across resume |
| `resume_lock_cancel` (rw, world-writable) | cancels that lock early |
| `force_power_off` (rw) | **not touched** |

Read on the device at 2026-09-04, uptime ~20 min:

```
resume_count      = 0
suspend_ts        = 0.000000000     resume_ts  = 0.000000000
spm_r12           = 0x00000000      eint_sta   = 0x0,0x0,0x0,0x0,0x0,0x0
```

**Every counter is zero: this unit has not completed a single suspend/resume since boot.** That is
the baseline any future test is measured against, and it means `spm_r12` after a test is
unambiguous — anything non-zero came from that test.

This is what a retry should be built around. The previous attempt had no post-mortem at all; the
reboot that ended it destroyed the only counters being watched. These nodes survive a resume and
name the wake source directly.

## 4. MTK's golden power settings — `/proc/mt_power_gs/`

`mt_power_gs_compare` @0xc03af4a0 walks two tables of `{volatile u32 *reg; u32 mask; u32 golden}`
and logs every register whose `live & mask` differs from `golden & mask`. One table is AP-side
memory-mapped registers, the other is PMIC registers read over `pmic_wrap`. Thirteen scenarios are
compiled in; the ones that matter here are `idle`, `dpidle`, `suspend` and `audio_playback`.

The tables are compiled into the image and are now extracted to
`analysis/kernel/power_golden_settings.txt` — 57 AP registers for `audio_playback`, 57 for `idle`,
126 for `dpidle`, plus 45 PMIC registers each. This is **MTK's own reference for what the SoC should
look like** in each state, which is a far better standard than reading registers and guessing.

The proc nodes exist on the device (`/proc/mt_power_gs/dump_*`) and a write arms the comparison for
that scenario; the deviations then print to dmesg. **Nothing was written to them** — the read
handler alone is a broken `seq_file` that repeats its own name forever (`cat` never terminates; use
`dd bs=64 count=1`), which is enough reason to characterise the write path from the disassembly
before using it.

## 5. What this does and does not settle

**Established (image data or read-only device reads):**

- The full SPM wake-source bit table and the shipped mask.
- KP is not armed; the keypad's own wake enable is switched off on suspend.
- The power key reaches SPM via MT6323 → EINT 150, and both the PMIC interrupt enable and the EINT
  wake-source bit are set.
- `slp_pwake_time` is writable and reaches `PCM_TIMER_EN` in hardware.
- This unit has never completed a suspend/resume; `icx_pm_helper` will say what happened when it
  does.
- MTK's per-scenario golden register sets, extracted.

**Not established:**

- Why the device did not come back on 2026-09-04. §1 makes "no wake source" *less* likely, not
  disproved, and offers no evidence at all about the resume path.
- Whether `PCM_TIMER` wakes through the R12 mask it is absent from.
- Anything about power actually saved. This unit has no `current_now`.

**The prerequisite for a retry is unchanged in substance but sharper in form.** It is not enough to
show a wake source exists in a register; the previous failure was caused by exactly that kind of
reasoning. What is needed is a suspend entered with `slp_pwake_time` set to a small value, **with
the user present and the device in hand**, so that a failure costs a button press rather than a
recovery. The first such test should establish only one thing: that `resume_count` becomes 1.
