this file records the code and flags the doc.

`docs/open-questions.md`, the `analysis/` RE writeups and the memory record; then verified
live — workspace tests, the launcher recovery matrix, the GLIBC gate on both shipped
binaries, dist-vs-source freshness, and targeted greps against the claims.

## 4. Findings

> **Doc-drift pass applied 2026-07-26 (same day):** F1, F2, F3 and F5 are **fixed** — see the
> resolution note under each. F4, F6, F7, F8, F9 remain open by design (they are work, not drift).
> The code fix in F3 is **comment-only**, so the `dist/` binaries are functionally identical and
> were deliberately **not** rebuilt: a rebuild would commit ~16 MB of binary churn for a comment
> (see F8). Source is therefore newer than `dist/` by two comment lines.

### F1 — STATUS.md's resume block is actively wrong (documentation, high impact)
The header says *"content current to 2026-07-03"* and the RESUME POINT says *"no code has
changed since the tenth round (2026-07-03); the workspace is clean."* Three commits have
landed since (07-25 USB-DAC discovery, 07-26 GPU + screenshot, 07-26 fonts + UI), carrying
the GPU path, the font fallback, the entire escape-ladder rewrite and the type-scale pass.
A reader trusting the resume block would flash a build believing it is the 07-03 build.
Body sections *were* updated for 07-26; only the header/resume block lies.

**FIXED** — the header is re-dated and the resume block now states the two facts that change what
the next flash means: Cinder is not installed (post-restore), and the flash carries the whole
unverified 07-26 batch.

### F2 — ROADMAP's "single next action" already happened
ROADMAP is stamped 2026-07-25 and declares the device session to be THE next action that
unblocks everything. That session ran (07-25 and 07-26) and returned real data — volume
control name and range, backlight node, input nodes and touch range, key codes, the live
MTPDB, the MSC root cause, the GPU uid-100 blocker. The P0 table still lists volume and
keymap as *"confirm/activate with a config drop"* when the discovery answers are already
baked in as defaults. The roadmap needs a rewrite around what the device sessions actually
left open, not a re-run of a completed step.

**FIXED** — rewritten around what the sessions returned vs what they left open. The next action is
now probe → reinstall → run the LDAC test; P0 is a *verify* table (not a data-gathering one);
volume/keymap are recorded as baked-in defaults; playlists and the `PlayEventListener` route moved
to P1 as offline work; the stale adb/amixer risks were replaced with the real ones.

### F3 — Stale TODO contradicts shipped code
`cinder-home/src/main.cpp:1176`: *"play-by-index needs TrackSequence RE — left as TODO until
the discovery/device session."* The `CINDER_ACT_PLAY_INDEX` case immediately below it drains
`cinder_pending_play_*` and calls `cinder_audio_play_tracks`. The comment is ~3 weeks stale.
A second stale comment sat on the volume case (*"No-op until `/contents/cinder_volume.conf` is
populated"*) when `load_vol_cfg()` has defaulted to the discovered control since 07-02.

**FIXED** — both comments now describe what the code does. Comment-only; binaries unchanged.

### F4 — A large unverified batch is queued behind one flash (process risk)
The device was wbrt-restored on 07-26, so **`/contents` was wiped and Cinder is not
installed**. The next flash will therefore carry *every* Tier-B change at once: new type
scale, new font path, new escape ladder, new MSC behaviour, GPU helper, screenshot hooks.
If that boot misbehaves, the bisect surface is the whole 07-26 day. This conflicts with the
project's own stated principle ("batch disruptive changes; don't leave it broken") — the
batching is fine, the *unverified* batching is what costs a recovery.

Mitigating: the escape ladder itself was rewritten in this batch, and rung 0 (cable at boot)
depends on nothing. `cinder-probe` can exercise render/db/audio/GPU with no lifecycle risk.
**Probe first, then flash** is more important on this flash than on any previous one.

### F5 — Device state after the restore is not written down anywhere
The wbrt restore rolled the whole eMMC back to the 2026-06-18 image: no cinder-home, no
launcher, no `/contents` flags, and the music library is whatever that image held. No doc
states the reinstall now needs **three** pushes (`cinder-home`, `cinder-umount`,
`cinder-gpunode`) plus the install `.UPG` — `cinder-gpunode` is new on 07-26 and appears in
`dist/` but not in any flash instruction.

**FIXED** — `RECOVERY.md` gained an "after a restore — what state you are actually in" section
with the three-push sequence, and STATUS.md STEP 2 now pushes all three and explains that a
missing helper degrades *silently* (the installer warns, it does not abort).

### F6 — Playlists remain unimplemented despite the schema being reachable
`build_library` hard-codes `playlists: Vec::new()`. The real MTPDB has been pulled and
analysed (`cinder-db` knows `.m3u8` rows are `media_type = 3` and filters them out as junk),
so the membership schema is now investigable offline — this is no longer device-gated in the
way the docs imply. It is the one user-reported bug from the 07-25 session (item 4) still
completely unaddressed.

**FIXED 2026-07-26** — schema RE'd against `artifacts/MTPDB_dev.dat` and implemented. There is no
playlist table: playlists are containers in a second object tree, with `object_type = 3` rows
pointing at tracks by `reference_id` in `child_index` order. Detection is by shape (a container
with type-3 children), not by `tree_id`, so it survives different tree numbering. Two traps, both
covered by tests: the `.m3u8` rows in the file tree are **decoys** (`child_count = 0`), and
deleting a playlist **orphans its entries** — 3028 of 3151 entry rows on the reference DB were
orphans, so the container join is load-bearing. `Db::playlists()`/`playlist_tracks()` → wired
through `build_library` → a playlist row plays the whole list in saved order over the existing
pending-play channel (no new FFI symbol, no C++ change). Write-up in
`analysis/H_mediastore/RE_findings.md`, which had this listed as an open RE item.

**Follow-on found while doing it:** the four **"Shuffle …" accent bands** (one per library tab)
are rendered but hit-tested nowhere — the largest touch target on each library screen does
nothing. Same mechanism as the playlist row; now cheap to finish. Added to ROADMAP P1.

### F6b — Touch-input sweep: rendered controls that were inert or mis-hit (2026-07-26)
Prompted by the shuffle-band discovery, every screen's renderer was compared against its hit test.
This device is **touch-only for navigation** (no d-pad), so a control that is drawn but not
hit-tested, or hit-tested somewhere other than where it is drawn, is a functional defect — not a
cosmetic one. Seven were found; all are fixed, each with a regression test.

| # | Screen | Defect | Fix |
|---|---|---|---|
| 1 | Library ×4 | The **"Shuffle …" accent band** — the largest target on each of the four tabs — was drawn but hit-tested **nowhere**. | `Action::Shuffle(ShuffleScope)`; resolved in cinder-ffi per scope. |
| 2 | EQ | **Preset pills were drawn at text width but hit-tested as five uniform 86px slots.** Tapping "A2" applied "JAZZ"; taps on blank space past the last pill still changed the sound. | Pills laid out on a uniform grid by `eq::preset_rect`, which render and hit test now share. Also makes the short names full-size targets. |
| 3 | EQ | The **raise/lower split was `y < 375`** while the zero line is drawn at the field midpoint (320). A 55px band below the line raised instead of lowering. | Split is `eq::FIELD_MID`, the drawn line. |
| 4 | EQ | Band columns were hit at **origin 22 / pitch 44** but drawn at **origin 30 / pitch 42**, so taps near a column edge hit the neighbour; the field was also live 150–600 while drawn 170–470. | `eq::band_at` / `band_center_x` / `FIELD_TOP` / `FIELD_BOTTOM`, shared with render. |
| 5 | EQ | Footer **"Reset"** drawn, hit-tested nowhere. | Wired (flattens all bands). "Save Sound Preset" is still inert — see below. |
| 6 | Up Next | **Every** tap returned to Now Playing, so the queue was look-but-don't-touch. | The renderer publishes the ids it drew (`up_next_rows`); a row tap plays that track. This is exact under the auto-scrolling window, which the hit test cannot recompute (it has no `np`). |
| 7 | USB-DAC | **A tap anywhere toggled the feature** — which switches the USB gadget mode and starts the LDAC bridge. A stray touch while reading the panel engaged it. | Only the switch toggles, via `usbdac::hit_toggle`, padded to ≥44px around the 34×18 drawn switch. |

Also closed a **gesture inconsistency**: swipe-to-queue worked on the Songs tab and inside an album
drill-in, but not on the Albums tab's expanded inline track rows — the same track queued on one
route and did nothing on another. Both now share `albums_track_at`.

**The underlying cause, in every case, is duplicated geometry**: the renderer and the hit test each
carried their own copy of the same numbers, and they drifted. This is the identical failure the
project already hit once with `library::row_h` (taps resolving to the wrong row on device). The fix
pattern is the same one that worked there — one exported layout helper, used by both sides:
`library::{shuffle_band_rect, hit_shuffle_band, album_play_band, list_top}`,
`eq::{preset_rect, preset_at, band_at, band_center_x, footer_at}`, `menu::row_at`,
`sound::row_at`, `up_next::{visible_row_at, window}`, `usbdac::hit_toggle`, and a single
`chrome::HEADER_BOTTOM` replacing the literal `91` that four screens had each hardcoded.
`menu`/`sound` were *correct* but duplicated — they now derive, and carry a `debug_assert` that
fires if the renderer's top ever drifts from the hit test's.

**Known-inert controls left deliberately** (documented, not silently broken): FM / BT Receiver /
Pairing screens (backend not RE'd — they are reachable and escapable via the back chevron), the EQ
footer's "Save Sound Preset" (the EQ is already persisted automatically on every change, so a
"save" button has nothing to do — resolve the wording or give it a real user-preset store), and the
Now Playing heart. The status-bar bookmark (Shelf) target is 26×34px, under the 44px guideline, but
it is bounded by the 34px status strip and a miss just opens the Menu, which is one tap to undo.

### F7 — Goal #3 has never been executed end to end
`ldac-bridge` builds, the vtable indices are extracted, the control sequence is written, the
UI toggle exists, and `TEST.md` has a three-outcome diagnostic table ready. Nobody has run
it. The founding feature of the project is the single largest untested surface, and its two
unknowns (does `SetCurrentSource(true)` open the server socket; is `hw:4,0` capture `-EBUSY`)
are both answerable in one session that does not require Cinder to be the Home app at all —
the supervisor runs under stock.

### F8 — Repository hygiene: 116 MB `.git` from committed binaries
18 build outputs are tracked, including two ~5 MB `.unstripped` ELFs that change on every
build. Every rebuild commits ~16 MB of churn. `dist/` artifacts arguably belong (they are
what gets flashed, and reproducibility matters for a device you can brick), but the
`.unstripped` pair and the loose `*.o` files are pure churn.

### F9 — GPU is one helper-install away and untested
The uid-100 EGL hang was root-caused precisely (four root-only device nodes), the fix
(`cinder-gpunode`, setuid, `lstat`-guarded, fixed path list, no argv) is written and built,
and the path is opt-in behind `/contents/cinder_gpu_on` so the default binary is unaffected.
It needs one safe probe run (`cinder-probe` with `CINDER_GPU=1` as uid 100). Note the
deliberate security trade-off: `chmod 0666` on `/dev/{ion,mtkfb_vsync,mtk_disp,sw_sync}`
world-opens graphics memory and display control. Acceptable on a single-user player, and
documented in the source, but it is a real loosening of kernel device permissions.

### F10 — Accuracy of the STATUS matrix itself
Spot-checked the "stationary" and "partial" claims against code: FM, receiver, pairing, BT
radio toggle, brightness slider, DB rebuild, playlists all verified genuinely inert as
described. The matrix is honest — its problem is the stale header (F1), not its content.

## 6. Overall assessment

The engineering is unusually disciplined for a firmware-mod project: object sizes reserved
from decompiles, a qemu construction preflight, a GLIBC ceiling gate, a sandboxed 18-case
recovery matrix gating the build, guarded IPC with crash+hang recovery, and an escape ladder
explicitly ordered by dependency after a brick taught that lesson. The RE is thorough and
written down. Nothing offline is broken.

The project's actual weakness is not code quality — it is **the ratio of written code to
device-verified code**, and the fact that the feature the project exists for (goal #3) sits
entirely in the unverified half. The docs compound this by describing the project as
"blocked on one device session" when two device sessions have since happened and produced
answers that have not been folded back in.

One session that runs the probe, reinstalls, and executes `ldac-bridge/TEST.md` would move
more of this project forward than any amount of further offline work.
