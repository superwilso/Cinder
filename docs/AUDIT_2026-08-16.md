# Cinder — full audit, 2026-08-16

Three questions, answered offline against the tree at `37e4121`+ (branch `feat/linux-adb-installer`):

1. **What is left to reach functional parity with Sony's stock player?**
2. **Is the queue and playback behaviour right?**
3. **Where is the CPU and the battery going?**

Companion to [`../cinder-home/STATUS.md`](../cinder-home/STATUS.md) (current state) and
[`../cinder-home/ROADMAP.md`](../cinder-home/ROADMAP.md) (forward plan). Prior audits:
[`AUDIT_2026-07-26.md`](AUDIT_2026-07-26.md), [`COMPARISON_cinder_wampy_sony.md`](COMPARISON_cinder_wampy_sony.md).

Offline gates at the time of writing: **253 host tests green**, 3 `#[ignore]`d benches.

> **Method note for §C.** Every performance number below is measured on the host with
> `cargo test -p cinder-ui --release --test render_bench -- --ignored --nocapture`, against a
> synthetic library at the device's real size (3648 tracks / 304 albums). Host numbers are not
> device numbers; this project's own established host↔device ratio is **≈14×** (a 1,080 µs host
> frame measured 16 ms on device, 430 µs measured 6 ms). Device figures below are that scaling,
> and are marked as estimates.
>
> The first draft of this audit guessed that `song_order`'s full-library sort was the dominant
> per-frame cost. **It is not — it is 32 µs, about 4% of a Library frame.** The bench found the
> real cost somewhere else entirely. That is the third time on this project a performance guess
> has been wrong by an order of magnitude, and it is why §C is measured rather than reasoned.
>
> A second draft then ranked the gradient-art bake (P2) first on the strength of the host bench —
> and **§E's device check demoted it**, because the art cache on this unit is complete, so almost
> no row actually draws a gradient. Host benches size a fix; the device decides whether it is worth
> making.

> **§E is a device pass**, run over adb at the end of this audit against the live unit. It closed
> two open questions outright, corrected one ranking in §C, and picked up one new defect.

## B. Queue and playing behaviour

### B1. The model is right

`context` (what is playing and what follows from it) is separate from `queue` (what the user
picked by hand), and PlayerService is handed `[current] + queue + context[idx+1..]`. That is the
correct model, it matches Apple Music, and the 2026-08-11 rework got it. The re-issue is deferred
to a **track boundary** because a mid-track `SetTrackSequence` restarts playback (device-measured),
and the position is restored either side. `up_next::layout()` being the single source of both the
drawing and the hit-testing is the right structural call. None of that needs revisiting.

Six defects underneath it:

### B2. Q1 — a queued track from the album you are already playing silently skips the middle of it

**Severity: high. Reachable in one gesture.**

At the track boundary, `cinder-ffi/src/lib.rs:3425` calls `set_context_playing(t.object_id)`
**before** it consumes the queue pick at :3429. `set_context_playing` looks the id up **in the
context** and moves `context_idx` to wherever it finds it:

```rust
match self.context.iter().position(|t| t.object_id == object_id) {
    Some(i) if i != self.context_idx => { self.context_idx = i; true }
```

So: play album track 2, swipe-queue track 8 of that same album. Track 8 plays next — correct — but
`context_idx` jumps 1 → 7, and the next `play_order_uris` returns `[track 8] + context[8..]`.
**Tracks 3, 4, 5, 6 and 7 are gone from the sequence.** The user asked to hear one song sooner and
lost five.

*Fix shape:* consume the queue pick **first**, and only fall through to `set_context_playing` when
the started track was *not* a queue pick. A queue pick must leave `context_idx` exactly where it
was — that is what "play next, then carry on where I was" means. Needs a regression test with an
id present in both lists.

### B3. Q2 — turning shuffle OFF does not restore the original order

**Severity: medium. Every user will hit it.**

`Action::ShuffleToggle` (`lib.rs:1696`) shuffles the remaining context when it goes **on** and does
nothing at all when it goes **off** — `self.context` stays permuted forever. Stock restores the
sequence. Right now shuffle is a one-way door: the only way back to album order is to re-tap the
album.

*Fix shape:* keep the unshuffled context alongside the shuffled one (or a permutation vector) and
restore it on the off edge, mapping `context_idx` through so the currently-playing track does not
move.

### B4. Q3 — there is no repeat-all, and the end of the queue is a dead stop

**Severity: medium. Known and already tracked in ROADMAP P1.**

Repeat is two states: off and one (`NodeTrackSequence::SetOneTrackMode`). When a sequence runs out,
PlayerService stops and nothing re-issues it. Stock has repeat-all. The shape ROADMAP already
proposes is right — detect end-of-sequence and re-issue from index 0 — and it needs one device
session to observe what the play state actually does when a queue empties.

### B5. Q4 — the sequence is silently truncated at 512 tracks

**Severity: low in practice, but silent.**

`play_pending_sequence` (`main.cpp:4555`) clamps to `static char bufs[512][512]`. "Shuffle all
songs" over a 3746-track library resolves 3746 URIs, hands over 512, and Up Next draws all 3746 —
the screen and the service disagree about the next 34 hours. It will realistically never bite, but
it currently produces **no log line at all**. At minimum log the clamp; better, window the sequence
and extend it at boundaries.

### B6. Q5 — the queue does not survive a reboot, and neither does playback position

**Severity: medium. A stock-parity item that reads as a bug.**

`context`, `queue`, `context_idx` and the play position are all in-memory. Stock resumes the last
track at its last position. Cinder boots to nothing playing. Everything needed is already
persisted-adjacent (`cinder_settings.conf` is written on every tap) — this is a serialisation
decision, not a research problem.

### B7. Q6 — a queue edit inside the last 2.5 s of a track re-issues mid-track

**Severity: low. By design, worth knowing.**

The pre-boundary flush (`lib.rs:2646`) fires when `duration - position <= 2500 ms`. Queue something
inside that window and the flush happens *now*, with a pause/seek/play round trip landing on the
last two seconds of the current song. The 2.5 s lead exists precisely to absorb it, so the artifact
is a hiccup right before a track ends rather than in the middle of one. Acceptable; noted so it is
not re-discovered as a mystery.

### B8. What is correct and was checked

- The pick is consumed at the boundary that starts it, so it cannot replay on the next re-issue. ✓
- `queue_shuffle` (MIX) moves only `context[idx+1..]` — the past and the now do not move. ✓
- `apply_shuffle` is applied to every **new** context, with the tapped track kept first. ✓
- `play_order_uris` puts `current` at index 0, so a re-issue does not change what is playing. ✓
- Reorder and swipe-to-remove both route through `QueueChanged` → the same boundary flush. ✓
- `queue_follow` re-arms on every new context and drops the moment the user scrolls. ✓
- `play_history` is bounded at 256 entries, so a long unattended session cannot grow it. ✓

## C. Performance — measured

Host, release, 3648 tracks / 304 albums. Device estimates at the project's own ≈14× ratio.

### C1. Where a frame goes

| Frame | Host | Device (est.) |
|---|---|---|
| Now Playing (either art path, post-07-28 optimisation) | 430 µs | ~6 ms |
| Library **Songs**, real covers | 260 µs | ~3.6 ms |
| Library **Songs**, gradient fallbacks | **708 µs** | ~10 ms |
| Library **Albums**, gradients | 633 µs | ~9 ms |
| Library **Artists**, gradients | **1,985 µs** | **~28 ms** |
| Library Artists, real covers | 792 µs | ~11 ms |
| **Up Next**, album-sized context (12) | 1,398 µs | ~20 ms |
| **Up Next**, shuffle-all context (3648) | **2,022 µs** + 523 µs of clone/layout in `nav::render` | **~36 ms** |

### C2. The derived state rebuilt on every painted frame

| What | Host cost | Rebuilt when it does not need to be |
|---|---|---|
| `context.clone()` in `nav::render` (Up Next) | **499 µs** | Every frame. Depends on nothing that changes between frames. |
| `up_next::layout` (shuffle-all context) | 24 µs ×2 | Built once in `nav::render` and **again** inside `render_view`. |
| The size-dependent slot walk in `render_view` | ≈600 µs | Walks all 3648 slots to draw ~14. |
| `az_present` (Songs A–Z rail) | **67 µs** | Every frame. Scans all 3648 titles to fill a 27-entry bool array. |
| `song_order` (Songs sort) | 22–45 µs | Every frame, **and once per `swipe_track` event during a horizontal drag.** |
| `albums_build` (Albums display list) | 6–14 µs | Twice per frame (once via `max_scroll_px` → `content_h`). |
| `albums_flat` | 1 µs | Four times per Albums frame. |

### C3. Findings, worst first

**P1 — Up Next clones the whole playback context every frame.**
`nav.rs:3410`, `self.context.clone()`. For a shuffle-all context that is 3648 `SongRow`s ≈ 15,000
String allocations, **499 µs host ≈ 7 ms device, per frame**, purely to satisfy the borrow checker
("Cloned rather than borrowed because the auto-follow below has to WRITE `queue_scroll_px`").

The mutation does not actually need the rows: `up_next_layout()` takes only `context.len()`,
`context_idx` and `queue.len()`. Do all three writes (`up_next_cur`, `queue_scroll_px`, `fling_v`)
first, then build `QueueView` borrowing `&self.context`. **The clone deletes cleanly.** This is also
the largest single allocation churn left in the app, on a heap whose churn has already caused one
on-device allocator abort.

**P2 — list-row gradient art is recomputed for every row on every frame.** *(Demoted by §E — read
that first.)*
The delta between the gradient and real-cover rows is the measurement: Songs 708 → 260 µs, Artists
1,985 → 792 µs. That is **~32 µs per drawn gradient**, ~450 µs of a Songs frame and ~1,200 µs of an
Artists frame. The 2026-07-28 pass already established the right fix for exactly this shape and
applied it to *one* place — bake the gradient once into the slot a decoded cover would occupy, so
drawing is a blit either way — and list rows never got the same treatment.

**But on a device with a warm art cache almost no row draws a gradient at all.** §E measured this
unit at *317 of 318 albums cached*, and `start_art_cache` loads the whole disk cache straight into
`Library::thumbs` (`cinder-ffi/src/lib.rs:2898`), so essentially every row is already a blit. This
is a **first-boot and artless-album** fix, not a steady-state one. Worth doing — the first library
scroll after an import is exactly when the device feels worst — but it is not the top of this list.

The Artists tab is still the slowest at **792 µs ≈ 11 ms even with real covers**, because it draws
an overlapping 1–2 cover stack per row. That is drawing more, not wasting more; there is no easy
win there short of drawing one cover instead of two.

**P3 — the Up Next draw loop is O(context), not O(visible).**
`render_view` walks all 3648 slots to draw the ~14 on screen (`continue` for everything above the
viewport). ≈600 µs host ≈ 8 ms device. `Layout` already stores each slot's content-space top in
ascending order — a binary search for the first visible slot makes the loop O(visible).

**P4 — the layout is built twice per Up Next frame.**
`nav::render` builds one for the auto-follow, `render_view` builds another. `render_view` already
*returns* its layout; have `nav` use the returned one, or pass one in.

**P5 — `az_present` scans the whole library every frame** to fill 27 booleans that change only when
the library or the sort chip does. 67 µs host ≈ 1 ms device. Memoize.

**P6 — `song_order` runs once per `swipe_track` event.**
`nav.rs:2170` → `library::song_at` → `song_order`. `swipe_track` streams during a horizontal drag,
so a swipe on the Songs tab sorts the whole library up to 60 times a second, on top of the render's
own sort. 22–45 µs each. Small individually; it is the *shape* that is wrong.

**The general fix for P1 and P4–P6 is one thing:** a memo on `App` holding
`(song_order, album_layout, az_present)` keyed on `(library generation, lib_sort, album_sort,
album_expanded)`, invalidated when the library is rebuilt or a chip is tapped. That removes every
row of §C2 except the gradient bake (P2) and the slot walk (P3), which are separate.

**Not a finding — checked and correct:**

- `cinder_render_tick` is properly dirty-gated; an idle screen costs nothing. ✓
- The frame canvas is reused, not reallocated (that bug already cost a reboot). ✓
- `cinder_audio_position` / `is_playing` / `listener_events` are cached atomics, **not** IPC. ✓
- `poll_now_playing` gates its binder round trip on the listener's callback count moving, so an
  idle device costs zero IPC. ✓
- The art builder yields 120 ms between albums, so it cannot compete with the render thread. ✓
- The cover decoder is a slot, not a queue, so five fast skips cost one decode. ✓
- Both per-frame IPC poll storms found on 2026-08-12 (`bt_poll_sound_status`, `uac_poll_status`)
  are throttled, with an immediate-poll escape on the events that can actually change the answer. ✓

## D. Battery

Measured baseline (STATUS.md, 30-second windows on device): dark+idle = 1.17% of a core system-wide,
Cinder 0.25%; dark+playing = 37.5% system, Cinder 0.43%. **The decoder dominates and always will**,
and the 230/s display-kthread context switches are a floor that is not reachable from userspace.
Cinder's own steady-state share is already about 1% of the total. So the levers left are not
CPU-shaving — they are *not running at all*.

| # | Lever | Now | Proposal | Why |
|---|---|---|---|---|
| B1 | **Auto power-off** | Does not exist | 15/30/60 min of no input **and** not playing → `SetStatus(PowerOff)` | A device left paused runs flat. Nothing else on this list is worth as much. Same §A gap #2. |
| B2 | **Idle screen-off default** | **OFF by default** | Default to 30 s | Deliberately opt-in because "a failed wake looks like a dead device". Wake is now proven three ways (touch, Power button, keys) and the auto-off path deliberately leaves the touch controller powered. The backlight is the largest continuous draw on the device and it is currently on forever unless the owner finds the setting. |
| B3 | **Audio pump rate, dark + playing** | 100 ms (10 wakeups/s) | 250 ms, i.e. the same as dark+idle | The pump only delivers binder replies for *our* client calls. Nothing waits on it faster than the 1 Hz housekeeping. Dark+playing is the longest-lived state a music player has, and this is now the largest single source of Cinder's wakeups in it (the render loop's `poll()` change already took that side to ~1/s). |
| B4 | **Awake-idle render rate** | 60 Hz `poll()` | 30 Hz when nothing is dirty and no contact is down | Real but small — the backlight dwarfs 30 wakeups/s. Only worth doing if it is free; **do not** risk drag smoothness for it. |
| B5 | **Every §C fix** | — | — | Less CPU per frame is less energy per frame. P2 (gradient bake) is worth the most because it is paid on every Library frame the user scrolls through. |
| B6 | **Low-battery shutdown** | Does not exist | Warn at 10%, clean shutdown at 3% | Not a saving — a *safety*. `/contents` is unjournaled vfat and Cinder writes the scrobbler log to it. |

The log's repeated `input: still ZERO events from every node (foreign grab?)` is **not** a fault —
that heartbeat fires on `g_ev_total == 0`, which is equally true of "grabbed by someone else" and
"nobody has touched it". The node diagnostics above it show every grab succeeding and no other
holder. It is honest but it cannot tell those two apart, and it reads as an error; worth rewording.

### E2. A new defect — the Hold switch is not detected if it is already on at boot

**User-reported during this audit, and diagnosed here.** Boot with Hold engaged and Cinder comes up
**unlocked**, and stays that way until the switch is flicked twice — in between, the UI's lock state
is the *inverse* of the physical switch.

Cause: evdev reports state *changes*, not the current level. `cinder_set_hold()` is only ever
called from an event in `input_pump` (`main.cpp:5177`); `input_open()` opens and grabs the nodes and
never asks what state the switch is in.

The device settles which ioctl to use, and it is not the obvious one:

```
$ getevent -p /dev/input/event4
  name: "icx_key"
  events: KEY (0001): 001c 0023 0031 …            ← 0x23 = 35, the Hold code
$ cat /proc/bus/input/devices | grep '^B: EV='
  EV=3  EV=b  EV=5  EV=9  EV=3  EV=100007  EV=3  EV=3
```

`icx_key` advertises **KEY only** (`EV=3` = SYN+KEY), and **no node on this unit exposes `EV_SW`
at all**. So Hold is an `EV_KEY`, and the initial state must be read with **`EVIOCGKEY`**, not
`EVIOCGSW` — a detail that would have cost a device round trip to discover later.

Fix: in `input_open()`, after the grab, `EVIOCGKEY` each node and test every code the **live**
keymap maps to `CINDER_BTN_HOLD` (not a hardcoded 35 — `cinder_keymap.conf` can move it). It must
run before the first paint, so a device booted on Hold shows the Lock screen rather than the
library.

Requested alongside it: **a software lock toggle**, where flicking it on and off resyncs the state.
Worth having on its own, and it is the manual recovery for any future disagreement between the UI
and the switch. The rule that must survive is STATUS.md's — *the physical switch is authoritative
and is the only thing that unlocks* — so the software toggle writes the same state and the next
switch event overrides it.

### E2b. A parked lead — "no backlight" is as bright as the lowest brightness

Also reported; deprioritised by the owner during the audit, so it is recorded rather than chased.
The code path looks correct: `recompute_day_level` sets `day = night = 0` at level 0, and
`set_backlight` has an explicit `if (cinder_get_brightness() == 0) level = 0;` that beats the
night-theme ternary. So the write is being issued and the panel is not honouring it.

The likely reason, read off the device: `/sys/class/leds/lcd-backlight` is a **PWM** backlight, not
a plain LED — `duty 21`, `frequency 32000`, `div 0`, and no `power` attribute. `brightness` maps
onto a duty cycle, and a nonzero duty floor in the driver would make 0 and 1 land in the same place.
One read settles it: write `brightness` 0 and read `duty` back. If it stays nonzero, the LED node
cannot reach off and the real switch is `duty` directly, or `DisplayService::SetLCDValidate(false)`
— already proven to work and to reverse (`cinder-probe --dispoff`). `/sys/class/graphics/fb0/blank`
is a known dead end here: accepted and ignored.

### E3. Two §A gaps stop being RE and become UI work

`amixer controls` on the CXD3778GF, values as read:

| numid | control | type | now |
|---|---|---|---|
| 28 | `headphone smaster gain mode` | ENUM `normal` / `high` | normal |
| 29 | `headphone smaster se gain mode` | ENUM `normal` / `high` | normal |
| 30 | `headphone smaster btl gain mode` | ENUM `normal` / `high` | normal |
| 11 | `l balance volume` | INT 0..88 | 0 |
| 12 | `r balance volume` | INT 0..88 | 0 |
| 13 | `master gain` | INT 0..30 | 30 |
| 25 | `output device` | ENUM off / headphone / line / speaker / fixedline | headphone |

So **A#8 (high gain) and A#9 (balance) are plain mixer writes**, on a backend Cinder already has
(`apply_volume`'s amixer path, including its control-name validation). Sony's `sid_4115
OutputSetting` is `output device`, and is worth *displaying* before it is worth writing — Sony's own
service may re-assert it, the way it does the FM analog mux.

### E4. The idle screen-off default, demonstrated

Measured over 30 s, summed across every thread of pid 353:

```
context switches: 146960 -> 150175   = 107/s
backlight:        255                 (full)
```

107/s is the **awake-idle** figure — a state STATUS.md's power sweep never characterised (it
measured dark-idle at 20.9/s and dark-playing). It decomposes cleanly into the 60 Hz render loop
plus the 20 ms audio pump, so it is what the code says it should be.

The number that matters is the second line. **The panel had been at full brightness for 21 minutes
with no input**, because the idle screen-off timer defaults to OFF. That is §D B2, on the owner's
own device, and the backlight dwarfs all 107 of those wakeups put together — which is also the
argument for *not* bothering with B4.
