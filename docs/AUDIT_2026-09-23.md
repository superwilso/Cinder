## Part B — Found and fixed

### B1. The boot guard's revert would write an `.appcfg` that appmgr cannot read

**Severity: high. It was live on the owner's player.** `cinder-guard.sh` is not shipped by the
installer, but it is installed by hand on the A55, and the device copy has the same logic as the
repository copy.

When the guard fires, it does `cat "$REAL" > "$APPCFG.guardtmp"` and then `mv` over the `.appcfg`.
Two facts were measured today:

* **init runs the guard under umask 077.** The guard's own state shows it. `/db/cinder-guard` is
  `drwx------` and its `count` and `log` are `-rw-------`, all created by the guard at boot. The temp
  file is therefore created `0600 root:root`, and `mv` keeps that mode.
* **appmgrservice runs as uid 100.** From the W1 dump (`processes.txt`, pid 421): `Uid: 100 100 100
  100`.

So the rescue would install an `.appcfg` that the Home-app launcher cannot read. The likely result
(inferred, not reproduced) is no Home app at all. The guard's own comment at that line calls this
"a far worse state than the loop this is escaping". It is the same class of bug as the 2026-09-21
W1 boot loop, where `/data/cinder` came out `0700 root:root` against a uid-100 launcher.

**Fix:** `chmod 0755` on the temp file before the `mv`. Stock's `.appcfg` is `0755 root:shell`.
**The device copy is still the old one.** Push it again with the steps in the file's footer.

### B2. The same missing chmod on the other two `.appcfg` restores

The install payload's **sanity-gate revert** (`install_cinderhome.sh`, FINAL SANITY GATE) and the
**uninstall restore** both do `cat .real > .tmp` and then `mv`, with no chmod. The forward write, a
few lines above the first of these, already does `chmod 0644`.

**Evidence class: defensive.** Whether these paths create a `0600` file depends on the umask of the
Sony updater, which has never been measured. The installer's own comments say it runs "as root with
umask 077" (the `VT_DIR` block). But #16's log shows the stock UI returning after an uninstall
through the updater, which points the other way. A live install from an adb root shell *is* 077
(per the memory notes and `DEVICE_SHELL_GOTCHAS.md`). The chmod costs nothing whichever answer is
true, so both paths now set `0755`.

### B3. A `/data` sentinel left by a live install makes the next `.UPG` install skip the cable pass

**Severity: medium. The stray was present on the owner's player** as `/data/.cinder_premount`,
0 bytes, timestamped 2026-09-22 20:33, the same minute as the live install that wrote the current
`.appcfg`.

The install payload drops a sentinel to tell a real `/data` mount from a write to the updater's
RAM disk. Since the 09-21 mount work it `touch`ed the sentinel **unconditionally**, and removed it
only when the mount failed. On a live system (`tools/cinder-install.sh`), `/data` is already
mounted, so the `touch` landed on the **real partition** and nothing removed it. The next updater
install then went wrong in this order:

1. It mounted `/data` correctly.
2. It saw the stray sentinel in plain sight and concluded `/data` was *not* mounted.
3. It stacked a second mount of the raw partition, still saw the file, and set `DATA_MOUNTED=0`.
4. It **skipped the cable pass**, with a false WARN in the log.

With the pass skipped, the first boot after the install lands on Sony's player with the cable in.
That is issue #14's symptom, brought back by its own fix. It heals after one bad install, because
the failed-mount branch removes the file.

**Fix, in both the install and uninstall payloads:**
* The sentinel carries this run's token (`cinder-premount $$`) and is only dropped when `/data` was
  not already mounted. An old 0-byte stray can no longer read as this run's marker.
* The sentinel is removed **unconditionally** once the answer is known.

`test_install_mounts.sh` gains a check that no sentinel is left on the partition after a live or an
updater run, plus two cases where a stray is already there. The mirrored block in
`test_cable_pass.sh` is updated to match.

**The new cases fail against the old logic:** 3 of 18 fail, verified by running the test with the
old block swapped back in.

### B4. The install mount-lifecycle test was never wired into CI

`test_install_mounts.sh` was added on 09-21, with the fix it pins, and `ci.yml` never ran it. It now
runs as its own step next to the cable-pass test. This is the same shape as SHORTCOMINGS §A3, where
the launcher matrix existed for weeks with nothing automatic running it.

### B5. The PC installer could not tell anyone why the player ignored the install

Two community reports show the same gap:

* **#16** (v0.3.9, stock 1.02): the install log is all successes, the player shows Sony's UI, and
  there is no `cinderhome.log` at all.
* **r/walkman, 09-21** ("-Fateless-", Mr Walkman): "boots into the updater for a second, but reboots
  back into Mr. Walkman".

The installer only reads the install log, so it can say nothing about either case. It now reads two
more things off the drive, and shows whichever is more urgent on the home page, the uninstall page
and the console:

* **Walkman One's `CFW/` folder.** On a player still running W1, the updater drops a package sealed
  for another model's KAS and says nothing (`reference_upg_kas_per_model`). The folder is user data
  and survives a revert to stock, so this is a **warning, never a refusal**.
* **The launcher's last breadcrumb.** Since 0.3.10, every hand-over to stock writes
  `cinderhome-launch: <reason> -> stock`. A breadcrumb *after* the last `main: start` is the story
  of the most recent boot.

Three new tests cover these. Their fixture lines are copied from the A55's own `cinderhome.log`,
not written by hand.

### B6. A doc comment landed on the wrong function

In `player/cinder-ui/src/nav.rs`, `set_device_base_fw` was inserted between `set_device_system` and
its doc comment. The new function carried "Seconds since boot and the kernel release." and the old
one carried nothing. Moved back.

## Part C — Recorded, not fixed

### C1. The "Latest" release does not start for a fresh installer

**This is the most important finding here, and it is a release decision, not a code change.**
v0.3.9 creates `/data/cinder` as root. Under umask 077 it is `0700`, and under 022 it is `0755`;
either way uid 100 cannot write it. The launcher then cannot record `bootcount` and takes the "state
cannot be written" escape to stock. v0.3.9 predates the breadcrumbs, so it leaves no line anywhere.
That matches #16 exactly.

The fix (`chown 100:100`, 77562fd) is device-verified on W1, but it shipped only in
**0.3.10-rc1 and 0.3.11-rc1, both pre-releases**. GitHub still serves v0.3.9 as Latest, so every new
user who takes the default download gets a player that ignores the install. A player that already
had a uid-100 `/data/cinder` from an older build is unaffected, which is why this passed on the
owner's device.

**Next:** cut the next stable with B1–B5 included. `tools/release.sh` repacks the `.UPG`s from the
changed scripts. Then answer #16 and the thread with the version to use.

### C2. Every install leaves the boot guard a false diagnosis

The installer removes `/data/cinder/bootcount` ("fresh install = enabled"). The guard runs before
the launcher and reads a missing count as "appmgr did not exec the launcher". So the first boot
after **every** install is logged as the 2026-09-21 failure and counted as unproven boot 1 of 3.
This is on the device: see the guard log at 2026-09-22 20:34:38, one minute after the live install.

The count resets on the next healthy boot, so the effect is a margin of two failed boots instead of
three after an install, plus a misleading log. Two ways to fix it, and neither was taken today
because the launcher matrix encodes the current meaning of "absent":

* Write `0` instead of deleting.
* Have the guard skip counting when an install marker is newer than its count.

### C3. The new shuffle rule has no test

`play_in_order` (tapping an album, playlist or channel turns shuffle off, and saves that) replaced
`apply_shuffle`, and the two `apply_shuffle` tests went with it. Nothing now asserts the new rule. A
`Render` cannot be built in a test, because it owns the framebuffer present path. So the testable
move is to pull the decision out into a pure function over `Np`, the way `batt_slew.h` did for the
gauge.

### C4. The mount tests mirror the block under test rather than extracting it

`test_cable_pass.sh` and `test_install_mounts.sh` each carry a hand copy of the installer's mount
block ("verbatim semantics"). B3 needed three edits for one change: the installer and both mirrors.
A future edit to the installer alone passes both tests while testing nothing.
`test_launcher.sh` already extracts the launcher from the installer's heredoc with awk; the mount
block could be fenced with markers and extracted the same way.

### C5. Small things

* `settings.rs` says the Firmware row "carries the VERSION as of 0.3.12" while `cinder_version!()`
  says `0.3.11`. `release.sh` will make them agree at the next tag.
* `cinder-guard.sh` uses `expr`, which is busybox-only on this firmware (`/system/xbin`).
  **Verified fine:** init's PATH includes `/xbin`, a symlink to `/system/xbin`. `$(( ))` would
  remove the dependency.
* No command-injection surface in the root paths. Every `system()`/`popen()` in `cinder-home` and
  `cinder-audio` formats only integers or compile-time constants. No filename, tag or Bluetooth name
  reaches a shell. The setuid helpers use absolute paths and pass each child its environment inline.

### E4. Recorded, not fixed

2. **A tap in Search still plays the album.** This is deliberate: search results mix songs,

### E5. 2038

The device clock is 32-bit and stays 32-bit: kernel 3.10, glibc 2.23, and `cinder-home` has to
link Sony's glibc C++ libraries. On 2038-01-19 03:14:08 UTC it wraps to 1901-12-13. What Cinder
could fix in userland is now fixed. Boot health and the helper timeouts measure durations with the
monotonic clock, and nothing compares wall-clock times for order any more (E3, rows 11–13). A
wrap therefore no longer latches the player into stock.

There are two ways to go further:

* **Era shift (Cinder-only; needs an owner decision).** From 2038 on, Cinder sets the device clock
  28 years back (883,612,800 s). Between 1901 and 2099 the calendar repeats exactly every 28
  years, with the same weekdays and leap years. Cinder then adds 28 to the year wherever it shows
  or records a date: the clock, scrobbles and likes. The cost is that anything Cinder does not
  own records the shifted date. That means FAT timestamps on `/contents`, Sony's database and
  logs. A PC would see new files dated 28 years early. This is why the decision is the owner's.
* **A real fix** needs a kernel with 64-bit time syscalls (5.1 or later on 32-bit ARM) and glibc
  2.34 or later built with `_TIME_BITS=64`. Sony's libraries are built against glibc 2.23. This
  is the "separate project" in `PRODUCTION_READINESS.md` N4, and nothing found here changes that.
