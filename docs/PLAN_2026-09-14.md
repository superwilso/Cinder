[`SHORTCOMINGS.md`](SHORTCOMINGS.md) (standing structural reference) and

**This is a healthy tree.** The gates are real, they run, and they pass. What follows is not a
rebuttal of that — it is what the gates cannot see.

### A1. The verification gap is still inverted, but much less than SHORTCOMINGS.md says

`SHORTCOMINGS.md` §A1 (2026-08-23) says 41% of the tree is "never compiled by any automated gate."
That is now **out of date in the project's favour** and should be amended rather than cited:

| Surface | Lines (tracked) | CI coverage today |
|---|---:|---|
| Rust | 47,975 | compiled + 549 tests |
| C / C++ | 30,509 | `-fsyntax-only -Werror`, 9 self-tests, 41 harness scenarios booting `main.cpp` |
| Shell | 6,807 | `shellcheck` (pinned) + `bash -n` + 55-case launcher matrix |

The honest residual claim is narrower and still worth making: **nothing in CI links or executes an
ARM build.** `host_syntax_check.sh` is `-fsyntax-only` — no codegen, no link, no ABI check. The
glibc-2.23 ceiling and the real cross-build live only in `build.sh`, which only `tools/release.sh`
calls. So a change that parses but does not link, or that raises the glibc floor, reaches a tag
before anything notices. `cinder-audio`'s IPC surface (the vtable offsets, argument shapes, object
sizes) remains untestable off-device, exactly as §A2 says.

### A2. `CLAUDE.md` is the most stale document in the repository, and it is the one read first

Its own banner is dated **2026-07-25** and states:

> *"Last code change was 2026-07-03 (tenth round); the tree is clean and the resume point is that
> device session."*
> *"The entire remaining critical path is device-gated and blocked on ONE thing."*

Since then: 53+ commits, v0.3.0 → v0.3.4 shipped, USB-DAC→LDAC executed end to end, palettes
device-verified, FM tuner, Bluetooth, NFC, playlists, keyboard, lyrics and search landed. The
file's "host tests green: 39 UI + 8 DB" is now 549.

This is **the identical failure the project already diagnosed and fixed for `ROADMAP.md`**
(`AUDIT_2026-09-01` §D2: *"A roadmap that is five weeks stale is worse than no roadmap, because
unlike a dated audit it is supposed to be current"*). `ROADMAP.md` got a banner; `CLAUDE.md` did
not, and `CLAUDE.md` is loaded into the context of every session automatically. Fixing this is the
single cheapest high-leverage action in this document.

### A3. 32 MB of stale preview PNGs are still committed, and `golden.txt` has made them redundant

### A4. Branch protection is on — and the owner is exempt from it

`AUDIT_2026-09-01` §D5 called branch protection *"the most important item in this document"*.
**It is applied** (checked through the API, 2026-09-14): `main` requires all six CI checks, strictly
(the branch must be up to date), and refuses force pushes. What it does **not** do is apply to
admins (`enforce_admins: false`) or require a review — which is why every one of the last 14
commits is a direct push to `main` (CI event `push`) and still lands. CI is green on all of them, so
this is latent, not active, harm.

For anyone else the gate is already real: an outside pull request cannot merge red. The open
question is only whether the owner's own pushes should go through it too — one API call
(`POST /repos/superwilso/Cinder/branches/main/protection/enforce_admins`), and after it every change,
the owner's included, needs a pull request with green checks.

### A5. The highest-consequence unverified code in the tree is shipping to strangers right now

`installer/src/stage.rs` sends the 12-byte vendor SCSI command itself under `#[cfg(windows)]`
through `IOCTL_SCSI_PASS_THROUGH_DIRECT`. Per `STATUS.md` (2026-09-12) it is *"compiled but never
executed on Windows"* — and since Sony's updater was removed, **it is the only way a Windows user
can install anything.** It is live in v0.3.4, which is what a Reddit link points at.

Downloads as of this audit: **2 Windows, 1 Linux.** The window to test it before it meets an
audience is open and small. `DEVICE_CHECKLIST.md` 11.9 already describes the test.

## Part C — The skins design system

**Decision recorded 2026-09-14: skins only.** Data-driven layouts (JSON/Lua/WASM) are out of
scope — `PLAN_skins.md`'s "Not recommended" section stands, and the owner has confirmed it. A skin
is Rust, compiled in, chosen in Settings.

This part **revises** `PLAN_skins.md` step 2. The goal, the three layers and the ordering are kept.
One thing in the stated contract is wrong, and it would break 229 tests on contact.

### C1. Where it starts from, measured today

| | 2026-09-11 (`PLAN_skins.md`) | **2026-09-14 (`7860396`)** |
|---|---|---|
| `nav.rs` total | ~13,000 | **13,267** (7,758 logic + 5,509 tests) |
| Coordinate-driven interactions in its tests | 213 | **229** |
| Screen modules | — | **44** |
| Screens answering taps with a named `Hit` | 8 | **6 modules** (`confirm`, `bluetooth`, `fm`, `library`, `pairing`, `shelf`) |
| Screens handed a `View` struct | — | **3** (`QueueView`, `SettingsView`, `DeviceView`) |
| Distinct font sizes at call sites | 314 literals | **24 distinct sizes**, `scale.rs` exists but most sites bypass it |

The shape of the problem is unchanged and the tree has moved *toward* the plan (`scale.rs` landed;
`golden.txt` landed). Two structural facts dominate everything below: **`nav.rs` is the only thing
that knows what a tap means**, and **layout is answered by 70+ small functions scattered across the
screen modules**.

### C2. The correction: layout is a pure function, not a side effect of painting

`PLAN_skins.md` specifies the hit map as populated *while drawing*:

> ```rust
> /// Draw one frame of `view`, registering everything tappable as it is drawn:
> ///     ui.hit(rect, Hit::Play);
> ```

**This cannot work on this codebase, and the evidence is decisive.** Of the 229 coordinate-driven
interactions in `nav.rs`'s tests, **exactly 5 call `render()` first.** Every other test constructs
an `App` and taps it without ever painting. Under "register as it is drawn," all of them would look
up a tap in an empty hit map.

The problem is not the tests — it is what the tests reveal about the design. Making hit-testing a
side effect of painting means:

* a tap before the first paint has no defined answer;
* a tap arriving after a state change but before the repaint is tested against **the previous
  frame's** geometry;
* hit behaviour becomes dependent on *paint order* and on clipping — a control under a clip or
  drawn off-panel silently stops being tappable;
* the headless suite, which is this project's fastest and most valuable gate, cannot run at all.

That last one is fatal. The 229 tests are the thing that lets a 13,000-line god object be
refactored safely.

**The fix keeps the actual goal.** The goal was never "register while drawing" — it was
*render and hit-test must not be able to disagree*, which is what killed the Menu chevron, the
Folders bar and the picker scrollbar. Single-sourcing achieves that; paint-time registration is
just one way to get it, and the wrong one here.

```rust
pub trait Skin {
    fn name(&self) -> &'static str;

    /// Resolve geometry for `view`. PURE: no Canvas, no side effects, no paint order.
    /// Both `render` and `App::tap` call this, so they cannot disagree.
    fn layout(&self, view: &View) -> LayoutMap;

    /// Draw, consuming the SAME LayoutMap the hit test will use.
    fn render(&self, c: &mut Canvas, t: &Theme, f: &FontSet, view: &View, l: &LayoutMap);
}

pub struct LayoutMap {
    regions: Vec<(Rect, Hit)>,   // named targets, in hit-priority order
    sliders: Vec<(Rect, SliderId)>,
    content_h: i32,              // for fling/clamp/scrollbar, owned by App
}
```

Consequences, all good:

* `App::tap` becomes `skin.layout(&view).hit(x, y)` → `App::on_hit(Hit)`. **No coordinates in
  `nav.rs`.**
* The 229 tests keep working unchanged — they tap an `App`, which resolves layout on demand.
* `LayoutMap` is *testable on its own*, which is what makes the contract suite in C4 possible: you
  can assert "every region ≥ 44 px, none overlapping" without rendering a pixel.
* Layout can be cached per `(screen, view-revision)` — the bench below says it needn't be, but the
  option exists and paint-time registration forecloses it.

**Cost is not a concern, and it is measured.** From `render_bench` on this tree (host x86; the
device is far slower, but both sides scale together so the *ratio* holds):

| | |
|---|---:|
| `up_next::layout` | **5.8 µs** |
| `up_next::render_view` | **249.4 µs** |
| `albums_build` | 4.2 µs |
| `library albums` (render) | 224.2 µs |
| `just canvas fill` (a blank screen) | 42.6 µs |
| Now Playing, cover page | **4,473 µs** |

Layout is **2.3%** of the frame it belongs to, and a blank canvas fill costs seven times more than
resolving Up Next's entire list geometry. Resolving layout on demand — even twice a frame — is not
where this app spends time. Cover art is.

### C3. Revised order

Step 0 (`golden.txt`) and step 1 (palettes) are **done and device-verified**. The rest:

| Step | What | Gate that proves it |
|---|---|---|
| **2a** | **Finish `scale.rs` migration** (B1 #8). Collapse the caption tier and row subtitles onto named roles | `golden.txt` re-blessed deliberately, with the 31-screen overflow matrix re-baselined **against rendered PNGs** — the caption tier *grows* on collapse, which is why it was deferred |
| **2b** | **`View`** — one enum over per-screen view structs. 3 of ~31 screens have one; the rest still take positional args | Compiles; `golden.txt` must not move |
| **2c** | **`LayoutMap` + `Hit`**, pure `layout()`. Migrate status bar, Now Playing and Menu first — smallest surface, and it retires the literal transport circles (`hit(240, 692, 44)`) | `golden.txt` unmoved **and** all 229 coordinate tests still green |
| **3** | The remaining screens, **Library last** (~300 references from `nav.rs`) | Same two gates, per screen |
| **4** | Extract today's screens as the `cinder` skin; add `--skin` to `cinder-host` and `cinder-sim` | A second skin renders without touching `nav.rs` |
| **5** | **First new skin — Terminal**, the furthest from Cinder, so it tests the contract hardest. `design/handoff_raw/nw-a55/project/screens-terminal*.jsx` already holds the design | The contract suite (C4) passes for it |

Steps 2a–2c are the whole risk. After them, each screen is mechanical and independently shippable.

### C4. The contract suite — what makes it a standard

One suite, run against every registered skin. Passing it is what being a skin *means*. Most of
these are now cheap because `LayoutMap` is inspectable without painting:

* nothing drawn off-panel (`tests/ui_overflow.rs` already does this for one skin — 31 screens × 2
  content sets × 2 themes × 7 UI scales);
* **every hit region ≥ 44 px, and no two overlapping** — a pure `LayoutMap` assertion;
* **every screen has a reachable way back** — the rule that would have caught the inert Menu
  chevron before a human did;
* **a screen whose list stops at `library::list_bottom()` draws the Now Playing bar** — the
  Folders/Up Next defect, already a rule, now enforced per skin;
* no panic on an empty library, hostile strings, night mode, or 140% UI scale;
* every palette that loads still meets its readability floors on the skin's surfaces;
* a per-skin `golden.txt`, so a skin's own changes are reviewed as pixels.

### C5. Safety — one gap worth closing

`PLAN_skins.md` notes a skin cannot touch the device, *"but a panic still ends the process, and the
device reboots into the escape ladder."* That is true and it is a poor outcome: **falling back to
Sony's firmware because a skin had a bad number** is a brutal failure mode for a cosmetic feature.

The project already owns the right pattern — the bad-boot counter. Apply it one level up: if the
app dies twice with skin *X* selected, revert to `cinder`, log why, and say so in Settings. An
unknown `skin=` in the settings file already falls back to `cinder` (the rule `Accent::from_index`
and the palette loader both follow). This extends that from "unknown" to "unsurvivable."

## Part D — Maintainer watch

**Decisions, 2026-09-14:** fixes go to a **draft PR** and never straight to `main`; **any** new
issue or bug report pings the owner; **GitHub is the channel** (a cloud session cannot read Reddit —
see below); device work happens by **script-and-paste**.

### D1. Reddit cannot be read from the cloud build environment — it can from the owner's machine

In the cloud session that wrote this, tested four ways: `WebFetch`, `curl https://www.reddit.com/...`,
`old.reddit.com`, and the `.json` API. All four fail identically at the proxy with
**`connect_rejected` — 403 to CONNECT (organization policy)**: an egress allowlist denying the
domain, which RSS shares. No workaround was attempted there, deliberately.

**That is a property of that environment, not of Reddit.** On the owner's own machine the thread's
Atom feed (`…/comments/1wedu23/.rss?sort=new&limit=100`, browser User-Agent) returns 200, and a
local session has been watching it alongside GitHub on 2026-09-13/14. The `.json` endpoints do 403
there too, and WebFetch is blocked for the domain, so the feed is the one route.

So the conclusion stands for anything **scheduled in the cloud**: funnel reports to GitHub Issues,
where the templates already exist and already route bricks/boot failures to `RECOVERY.md` and
`SECURITY.md`. A local session can keep reading the thread directly.

### D2. What the watch does

An hourly Routine wakes a session that:

1. lists new/updated issues, issue comments, PRs and PR review comments on `superwilso/Cinder`,
   ignoring anything authored by the owner or a bot;
2. for anything new: reproduces it if it can be reproduced off-device, writes the fix, runs
   **all** gates (549 tests, 41 harness scenarios, syntax check, `golden.txt`), pushes a branch and
   opens a **draft PR**;
3. **drafts** a reply with the diagnosis and the PR link, and hands it to the owner — it does not
   post it. Anything said in public on the project is in the owner's own words;
4. **pings the owner's phone** — on every new report, per D's decision, whether or not a fix landed,
   with the draft reply attached;
5. if it is device-gated, writes a self-contained diagnostic script, says so, and does not guess.

**The boundary it does not cross:** nothing merges to `main`; nothing is posted publicly in the
owner's name; nothing is pushed that fails a gate;
anything touching the boot path, the installer, root helpers or Sony IPC gets a diagnosis and a
proposed patch rather than a speculative fix, because CI cannot execute that half of the tree
(A1) and a wrong guess there costs a device with no public recovery path.
