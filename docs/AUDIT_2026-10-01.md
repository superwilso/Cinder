# Cinder and Flint — audit, 2026-10-01

**Against Cinder `1976b71` (v0.3.14, the Latest release) and Flint `d095f7d` (v0.2.1 plus its
*Unreleased* palette work).** This is the first audit to take both repositories together. It covers
the 0.3.12–0.3.14 code that no general audit has read (the last one, `AUDIT_2026-09-23.md`, was
against `be1521b`/`cf0f20f`; `AUDIT_2026-09-28_power_sound_w1.md` covered power and sound only).
It also reads Flint end to end and tests the contracts between the two programs.

**Evidence classes, per claim:** *measured* (a number was taken here), *reproduced* (the defect was
made to happen on this machine), *read* (established from the code, not executed), *inferred*
(reasoned, not run). No device was attached to this pass, so nothing below is *device-verified*
unless it cites an earlier device run.

## Part C — Cinder: recorded, not fixed

### C1. Stable releases carry features that have never run on a device

v0.3.12 (09-23), v0.3.13 (09-29) and v0.3.14 (09-30) are all stable, and 0.3.14 is GitHub's
Latest. The CHANGELOG is honest about what each entry has been through, and by its own words the
following shipped in a stable release while *host-tested only*:

* **0.3.14:** Library views (checklist §22), Now Playing styles (§23), the PCM-tap visualiser
  (§24), and **Use Sony's receiver** (21.10).
* **0.3.13:** the linear headphone amp ("the switch itself has not run on a device yet"), and the
  DAC EQ, which was accepted by the chip but which nobody has listened to or measured.

Two of these are more than a new screen:

* **The PCM tap changes a default.** Sony's AudioAnalyzerService is no longer started for library
  playback. If the tap misreads on some file, the fallback is graceful (C3), but the default path
  for every user is the unverified one.
* **Use Sony's receiver writes Sony's stored configuration** (group 5008, key 5039 →
  `kFuncBtReceiver`) and reboots into stock. The code is careful. It writes the restore flag and
  `sync()`s before the change, refuses to act if it cannot read the old value, and the restore is
  one-shot (`main.cpp` `sony_rx_write`, `sony_rx_restore_at_boot`, *read*). It is still a write to
  Sony's persistent state that no device has executed.

This is the argument `PRODUCTION_READINESS.md` keeps making: a stranger takes the default download.
**Recommendation:**
* Keep stable for what has passed its checklist row, and ship the rest as `-rc` pre-releases (the
  channel exists, and 0.3.10/0.3.11 used it).
* Or ship untested features default-off.
* Either way, have `tools/release.sh` list the open checklist rows that the release's CHANGELOG
  entries cite, so the choice is made with the list in front of you.

### C2. The Windows installer's install path has not passed since it was replaced

Checklist **11.9** was re-opened 2026-09-12, when the Windows installer stopped launching Sony's
updater and began sending the vendor SCSI command itself through SCSI pass-through. It is still
open. Three stable releases later, that path is the only way a Windows user can install, and no
row records it working end to end.

There is one piece of field evidence that might close half of it. #16's reporter wrote on 09-24:
"I tried v0.3.12 and it boots fine now." Their operating system is not stated. **Ask them**, and if
it was Windows, record it against 11.9 with the caveat that the update, uninstall and reinstall
steps are still unseen.

### C3. The PCM tap's edge cases (inferred)

`pcm_tap.rs` reads the slot timestamp as a 32-bit field (`i32_at(240) as u32`), in µs from the
start of the track. A `u32` of µs runs out at **71 min 35 s**. Past that, no slot covers the
playback position. The tap returns `None`, `tap_fresh` lapses after 1.5 s, and the analyzer takes
over. So:

* the visualiser does not break;
* it pauses for about 1.5 s, then drops to the analyzer's bands, and the *Bands* setting silently
  stops meaning anything for the rest of a long mix or audiobook chapter.

If +244 is the high word of a 64-bit timestamp (the dumps cannot say: every track sampled was
short), reading it fixes this. Add a 75-minute file to §24.

Second, `find()` takes the lexically first matching file. A PlayerService that dies leaves its
`/dev/shm` queue behind, and its PID sorts as text: `PID_1234` comes before `PID_987`. So a stale
file could be the one chosen, on every search, until reboot. The fallback again hides it, but the
tap would be dead for that boot. Prefer the newest `mtime`.

## Part E — Flint: findings inside Flint

Flint is well built for its size. It has no dependencies. Its FLAC and ID3 writers refuse what
they do not understand rather than half-rewriting it, and they write through temp file, `fsync`
and rename. A file whose tag cannot be read gets no content key, so it is copied untagged rather
than failing. The shared-palette index is sanitised so that no line can become a path outside the
folder, and network access is https-only. The findings:

**E1. Stop during Copy did nothing (fixed, B2).** *Read.* The window offered Stop during Copy
(`stop_target(Tab::Sync) == Some(Job::Apply)`). The job recorded the click in a variable it then
discarded (`let _ = cancelled;`), and `apply()` had no way to be told. Every file was copied, and
the closing sentence said "Stopped early."

**E2. Copy re-plans rather than carrying out the plan shown (open).** *Read.* `Job::Plan` and
`Job::Apply` both run `sync_job`, which scans the library and the player afresh. The README
promises "Copy is only offered for a plan you've just seen", and that is enforced only against
settings changes. A folder deleted from the library, or music added to the player, between
**Show** and **Copy** produces removals nobody was shown. **Recommendation:** keep the `Plan` from
the preview and have Copy apply it after a cheap staleness check. Re-scan, compare the copy and
removal sets, and refuse with "the player or the library changed — look again" when they differ.

**E3. Partial files leaked (fixed, B3).** *Read.* `copy_plain`, the path every untagged file takes,
did not remove `.name.flint-partial` on failure, unlike the FLAC and MP3 writers. A pulled cable
leaves one behind on any path. The scan skips names starting with a dot, so nothing ever found
these files again. Each one holds the space it took, on the volume that is usually full when a
copy fails.

**E4. The planner was quadratic (fixed, B4).** *Measured.* `preferred_volume` walked every file on
the volume, and `format!`ed a string for each, once per album group, then did it again for the
bytes. Part B has the numbers. Plan and Copy each run it once per volume.

**E5. Every plan read every MP3 in full (fixed, B5).** *Read.* The sync's `tag_for` called
`cache::content_key` for every track. For an MP3 (and for a FLAC with no STREAMINFO MD5) that is
an FNV hash of the whole audio. The cache has a `(path, size, mtime)` fast path for exactly this,
and its own doc says so, but only `flint scan` and the Music Center import used it.

**E6. Smaller sync defects (fixed, B6).** *Read.*
* `choose_volume` said "ties go to the earlier volume (internal memory first)", but `max_by_key`
  returns the *last* of equal keys. With `--gb 10 --gb 10` and two empty volumes, the first group
  went to the card.
* `if out.copied % SAVE_EVERY == 0` is true at `copied == 0`, so every failure before the first
  success rewrote every manifest.

**E7. The unit that "moves together" is the top-level folder (open, design).** *Read.* An album is
`rel.split_once('/').0`. Flint's own scan test uses `Artist/Album/01.flac`, for which that unit is
the **artist**. A large discography then moves as one, can fit on neither volume, and is skipped
whole. The README says "albums move as a unit". Either say "top-level folders", or make the unit
the folder that holds the audio and keep the playlist grouping on top.

**E8. Playlist reading (open).** *Read.*
* Relative entries are resolved against the **library** root, not the playlist file's folder,
  which is what M3U means. That works for Sony-sync's layout, not for a MusicBee or foobar export
  kept in `D:\Playlists`.
* One playlist that is not valid UTF-8 (a legacy `.m3u` in the Windows code page) fails the whole
  sync: `read_to_string`'s error is returned. Fall back to Latin-1/CP-1252 the way Cinder's
  `parse_file` falls back to `from_utf8_lossy`.

**E9. Refused scrobbles stay in the log forever (open).** *Read.* Rows Last.fm refuses are kept and
sent again on every run. That is right for Last.fm's ignored-message code 4 (*timestamp too new*, which F2 produced
for anyone east of UTC) and wrong for code 3 (*timestamp too old*, past the 14-day window), which
can never succeed. Move
code-3 rows to `.scrobbler.refused.log` with the reason, and keep the rest.

**E10. CI (open).**
* `ci.yml` runs on `push: ["**"]` **and** `pull_request`, so every push to a branch with a PR
  runs twice. That is the shape Cinder's `ci.yml` removed.
* The debug-build lossless test takes 25 s. Add `[profile.dev.package.flint-core] opt-level = 3`,
  or test `flint-core` in release.

**E11. Small (open).**
* `http.rs` says "Last.fm is the only thing on the other end". `raw.githubusercontent.com` is one
  too now.
* The shared-palette shop opens a new WinHTTP session per file: up to 200 TLS handshakes. Reuse
  the session, or have cinder-themes' CI publish one bundled file.
* On Unix, `lastfm.conf` is written with the default mode and then `chmod 0600`, which leaves a
  moment when the secret is readable. Create it with the mode instead (`OpenOptionsExt::mode`).
  This affects development only; on Windows the file sits in the user's own profile.

## Part F — The contracts between Cinder and Flint

| Contract | Cinder side | Flint side | Verdict |
|---|---|---|---|
| Where music lives on the player | Sony's scanner and both device proofs use `/contents/MUSIC` | Sync mirrors the library into the **drive root** and sweeps it | **F1 — broken** |
| `.scrobbler.log` | `#TZ/UNKNOWN`, local wall-clock (`scrobble.rs`) | ignored the header | **F2 — broken, fixed** |
| Palettes | `palette.rs`, `theme.rs` | a port, `palette.rs` | F3 — agrees (200,000 cases) |

| Playlists | basename + suffix resolution | library-relative paths at the volume root | F5 — fine |

### F1. One "player drive", two meanings (High; reproduced; open)

The window asks for "the drive the player appears as", and the README's examples say
`--to E:\ --to F:\`. That one path is then used as:

* **the drive root** by scrobbles (`.scrobbler.log`), likes (`cinder_loved.tsv`, and
  `likes::Volume::music_dir()` = `<root>/MUSIC` for the liked playlist and for indexing music), and
  palettes (`cinder_palettes/`);
* **the music root** by the sync: copies go to `<root>/<library-relative path>`,
  `flint-manifest.tsv` sits at `<root>`, and the sweep removes every audio file under `<root>` that
  the plan does not put there.

The sync's rules were inherited from the Python `Sony-sync`, whose root was `/contents/MUSIC`.
Cinder's `PLAYLISTS.md` and Flint's own `MANAGED_PLAYLISTS` ("Liked Songs", which Flint writes into
`MUSIC/`) both assume that root.

**Reproduced** (Flint `d095f7d`, a scratch player with music in `MUSIC/` and a loose playlist):

```
$ flint sync <lib> --to <player> --gb 1
plan: 1 to copy (0 tagged with SensMe data), 3 to remove, 0 playlists to write
  would remove  <player>/MUSIC/Old - Album/01.flac
  would remove  <player>/MUSIC/Old - Album/02.mp3
  would remove  playlist my-device-playlist.m3u8 (<player>)
  would copy    Artist - Album/01.flac
```

What follows on a real player, if the owner presses Copy on that plan:

1. **Everything in `MUSIC/` is deleted.** That includes Music Center transfers, drag-and-drop, and
   a Sony-sync library. Music that is not also in the PC library is gone. The budget arithmetic
   counts it as free space (`free + on_device`), and the sweep runs first, so the plan fits.
2. **The library lands at the drive root, outside `MUSIC/`.** Whether Sony's scanner indexes it
   there is *unverified*: both device proofs (RE §9, checklist 14.1) copied into `/contents/MUSIC`.
3. **Flint's own liked playlist comes out empty.** `index_volume` walks only `MUSIC/`.
4. Cinder's own playlists survive: they live in `cinder_playlists/`, and Cinder resolves entries
   by basename, so moved files still resolve.

The dry run lists the removals: the first 12 in 0.2.1, and every one up to 1,500 in Flint's *Unreleased*. A careful owner sees them. It is
still the default path the documentation teaches, and it ends in irreversible deletion.

**Options — the owner's decision, so nothing was changed:**

1. **Root the sync at `<drive>/MUSIC`** (`likes::Volume::music_dir()` already resolves `MUSIC` or
   `Music`). Keep the drive root for the Cinder files. Migration: a manifest found at the drive
   root means an earlier Flint synced there. Offer a one-time move, which is a rename on the same
   FAT volume and therefore instant.
2. **Sweep only what the manifest says Flint wrote**, with `--sweep-unowned` and a window checkbox
   to opt in. Flint already applies exactly this rule to sidecars: "sweeping them would delete
   files another tool — or the owner — put on the player".
3. At the least, make Copy confirm when the removals include files Flint never wrote, giving their
   count and total size.

The recommendation is **1 and 2 together**. Until then, the README and the window should say
plainly what a sync owns.

### F2. Scrobble times off by the time zone (fixed on Flint's branch)

Cinder's `scrobble.rs` explains that the device has no time zone. `clockset` builds the epoch from
the typed wall clock as if it were UTC, so the log declares `#TZ/UNKNOWN`, and that tells the
uploader to apply its own zone. The 2026-09-06 report ("the scrobble time clock is wrong") was
fixed on that basis. Flint's `scrobblelog::parse` kept the header and never read it, and
`client.scrobble` sent `parts[6]` raw.

The result was every play off by the PC's UTC offset: an hour in a UK summer, nine hours in Japan.
For anyone east of UTC, a play uploaded soon after it happened was *in the future*. Last.fm ignores
those (code 4), and Flint kept them to send again.

**Fix (B1):**
* `Log::local_time()` reads the header.
* `lastfm_sync::to_send` converts a copy of each batch with `localtime::local_to_utc`. That is a
  two-step guess-and-correct over the OS's offset at an instant, which lands on the right side of
  both daylight-saving changes (tested against the UK rule for 2026).
* Refusals are matched on the converted copy, and rows are removed by the original, so the log's
  rows are untouched.
* A `#TZ/UTC` log is sent as written. Logs from before 09-06 that say `UTC` but hold local times
  stay as wrong as they declare.

### F3. Palettes — agree (measured)

A differential test linked both crates: `cinder_ui::palette::Palette::parse` against
`flint_core::palette::check_file`. It ran on 200,000 generated files, with random keys, colours in
five spellings, junk lines, bad ids and names, and dark/light bias so that some pass. The verdicts
**agreed on all 200,000** (7,893 accepted by both). The constants (sizes, floors, the six accents,
the night dim) were also compared by hand and are identical. Flint's claim to give "the player's
verdict" holds today.

**Keep it holding:** Flint's module says "if the two ever disagree, the player is right and this
file is the bug". Make that a test rather than a sentence (G1.7).

### F4. Liked songs — identical, not pinned (measured)

`NOISE`, `FEAT_MARKERS`, `ARTIST_SPLITS` and the punctuation folding were extracted from both files
and compared: all identical. But no test crosses the two repositories, and a one-sided edit makes a
like "cross in one direction and come back as a different track" (Flint's own comment). A shared
file of `(artist, title, expected key)` vectors, checked by both test suites, pins it (G1.7).

### F5. Playlists — fine (read)

Flint writes library-relative paths at the root of the volume it syncs. Cinder's
`tracks_by_filenames` resolves by basename, then by suffix, so relative and absolute entries both
resolve, and so do files that later move.

### F6. SensMe — device-proven for FLAC and MP3; M4A is a gap

Flint writes the FLAC `SMFM` application block and the MP3 `GEOB USR_SMFMF` frame, and both were
device-proven in September (RE §9, §10). The player also parses MP4 (`MP4Parser_readSmfmf` in
`libMediaStoreService.so`, RE §4), and Music Center writes it there through
`OmgMp4LibWrapper.dll`. Flint copies M4A/AAC/ALAC untagged (G3.7).

### F7. Files the player cannot decode

Cinder 0.3.13 refuses to hand PlayerService a FLAC wider than 24 bits. libFLAC 1.3.2 stalls the
service on one, and the result was "AUDIO STOPPED — RESTART" until reboot. Flint reads STREAMINFO
on every FLAC anyway, and still copies these files to a player that will skip them (G1.3).
