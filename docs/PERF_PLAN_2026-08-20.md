# Performance plan — the remaining list-render cost

*Written 2026-08-20 against measured numbers, not against the 2026-08-16 audit's estimates. Every
figure below is `cargo test -p cinder-ui --release --test render_bench -- --ignored --nocapture` on
the host, today, after the work that has already landed. Host numbers are not device numbers; the
RATIOS transfer, the absolutes do not.*

## Already done — do not redo

* **P1, the Up Next context clone.** `nav.rs` used to `self.context.clone()` every frame so the
  auto-follow could write `queue_scroll_px`; it now computes the scroll from three numbers
  (`up_next::metrics`) and takes a shared borrow afterwards. The 623 µs line above is the bench
  still measuring a deliberate clone as a reference point — the app does not pay it.
* **P6 (half), the A–Z rail.** `nav::az_present_memo` caches the 27-bucket map keyed on
  (tab, songs sort, albums order). The 68 µs `az_present` line is the uncached primitive.
* **The gradient blit primitive.** `art::gradient_image` renders a gradient once into an `Image`;
  Now Playing's cover already uses it. The list rows do not — see P2.

## Landed since this plan was written (same day)

* **P2 — done, and it was not where this plan said it was.** The list rows already had a gradient
  cache; what did not was the album drill-in's 96x96 cover, the Playlists rows and Now Playing's
  night header, each recomputing a gradient every frame. The cache moved out of `library.rs` into
  `art::block_cached`, beside the function it memoises, and those three now use it. Playlists tab
  **231.9 -> 152.6 us/frame**. It declines above a 128 px edge: one 480x480 entry is 691 KB, and
  this device has aborted an allocator over render-path churn before.
* **P3 — done.** `Layout::at` is a `partition_point` rather than a linear find, with
  `at_matches_a_linear_scan_everywhere` sweeping every pixel of four layouts against the old
  answer, including the gaps between sections where it must be None.

## The work, in the order worth doing it

### 1. P2 — gradient tiles for list rows *(DONE — see above)*

**Where.** `art::block` (`cinder-ui/src/art.rs:269`) is called once per visible row per frame from
every library tab and drill-in (`library.rs` `thumb()` / the Playlists arm). It costs real work per
pixel: a ramp lookup, a squared-distance test and a `sqrt` inside the highlight disc. Fourteen
48×48 rows is ~32k pixels of that, every frame, on tracks with no embedded cover.

**Design.** An LRU of pre-rendered tiles, keyed by `(name hash, w, h, theme is_night, opacity)`,
holding `art::Image`s built with the existing `gradient_image` and blitted with the same path real
covers use. Size it at 20 entries: a screen shows ~14 rows, and 20 × 48×48×3 B ≈ **138 KB**, which
is the whole memory cost of the change. Evict on theme change rather than keying every lookup on a
palette (two keys are enough: day and night).

**Expected.** The per-pixel work disappears from the frame and becomes a memcpy: artists ~450 → well
under 100 µs, and the same shape for the other three tabs. Verify with `bench_library_tabs` before
and after; the "(real covers)" lines are the floor this can approach, not beat.

**Risk.** Low, and bounded by memory: this is a cache in front of a pure function, and the pixels
are identical by construction. The one thing to get right is the key — a tile keyed without the
theme would paint day tiles on the night screen.

### 2. P3 — binary-search the slot walk

**Where.** `up_next::Layout::at` (`up_next.rs:264`) and `top_of` (`:275`) are linear `find`s over
one slot per track. After "Shuffle all songs" that is the whole library, and `at` runs on every tap,
every drag frame of a reorder, and every swipe classification.

**Design.** `slots` is already sorted by `top` and each slot's height is known, so `at` is a
`partition_point` on `top` followed by one bounds check. `top_of` needs the same treatment or an
index; it is called once per lifted row, so it matters less.

**Expected.** O(n) → O(log n) on the interaction path, not the paint path — this is about the drag
staying smooth on a 3,463-slot list rather than about frame time.

**Risk.** Low. `metrics_matches_layout` already sweeps the arithmetic twin against the built layout;
extend it to assert `at()` agrees with a linear scan across the same sweep.

### 3. P4 — stop materialising the layout to paint a window

**Where.** `up_next::render_view` (`up_next.rs:350`) calls `layout()` per frame — 33 µs and ~29 KB
of slots to draw the ~14 rows that fit on screen.

**Design.** `metrics()` is already the O(1) arithmetic expression of the same geometry and is
already tested against `layout()`. Give it a `slot_at(content_y)` and walk the visible window from
the first visible slot, so nothing is allocated per frame. Keep `layout()` for the reorder drag,
which genuinely wants the whole map, and keep the sweep test as the contract between them.

**Expected.** 33 µs and the allocation churn out of every Up Next frame. The remaining ~320 µs of
`render_view` is row drawing, which is P2's territory (those rows draw gradients too).

**Risk.** Medium — this is the geometry that four interactions share, and the audit's own warning
was that a renderer and a hit test drifting apart is this UI's recurring bug. The mitigation is that
`metrics` and `layout` must keep agreeing, and there is already a test that says so.

### 4. P5 — memoise `song_order`

**Where.** `library::song_order` (`library.rs:781`) sorts up to 3,463 indices; 30–57 µs depending on
the sort. It is called from `render`, from `song_at`, and from every hit test that resolves a row.

**Design.** The same shape as `az_present_memo`: cache `Vec<usize>` on `App`, keyed by
(sort, filter genre, hi-res filter, library generation). "Library generation" needs a counter bumped
by `set_library` and `set_playlists` — cheaper and harder to get wrong than hashing the library.

**Expected.** Two to four of these per frame collapse to one clone-free borrow. Smaller than P2, but
it also removes the same work from every tap.

**Risk.** Low-medium: a stale memo shows the wrong track for a tapped row. The generation counter is
the whole safety argument, so bump it in exactly the two setters and nowhere else.

## Not in this plan

* **The 6.8 ms cover frame.** That is album-art decode/scale, already understood, and it is paid on
  track change rather than per frame. Different problem, different pass.
* **Device measurement.** Every number here is the host. The device is the machine that matters and
  the ratios are what transfer — re-run `bench_library_tabs` and `bench_derived_state` on device
  before and after each item, exactly as the 2026-08-16 audit did, and put the numbers in the commit.
